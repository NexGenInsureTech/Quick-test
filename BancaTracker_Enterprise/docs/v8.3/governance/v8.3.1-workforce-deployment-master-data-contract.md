# BancaTracker Enterprise v8.3.1

## Corrective Contract — Workforce Deployment v2 Master Data Exposure

**Status:** Corrective-release contract
**Baseline:** Frozen `v8.3.0` commit `2130d8b2d2e7d29dabf9f1ead83c89880b9bd43f`
**Scope:** Expose an already implemented native Workforce Deployment v2 authority in Master Data Administration. No authority, persistence, resolver, or analytics redesign.

## 1. Objective

v8.3.1 must make native **Workforce Deployment v2** an explicit, uploadable Master Data choice while preserving the existing **Branch Assignment (Legacy)** choice and its RM-centric compatibility behavior.

The correction is presentation and discoverability work. The native import, validation, persistence, reload, effective-date resolution, and legacy-isolation paths already exist and remain authoritative.

## 2. User-facing identity

Master Data Administration must show two unmistakable choices:

| Choice | Contract | Purpose |
| --- | --- | --- |
| **Workforce Deployment v2** | Native effective-dated deployment | Where an employee is operationally deployed; `PRIMARY`/`SUPPORT` coverage. |
| **Branch Assignment (Legacy)** | Legacy branch-to-RM assignment | One legacy RM assignment for a branch; compatibility authority only. |

The UI must not call Workforce Deployment an RM ownership model, Branch Assignment, a business-owner master, or an attribution mechanism.

## 3. Canonical persistence identity

Both profiles continue to use the existing canonical identity:

```text
dataset type: BRANCH_ASSIGNMENT
store: branchAssignments
```

The active dataset’s existing metadata distinguishes the native profile:

```text
dataContract.name          = BRANCH_ASSIGNMENT
dataContract.version       = 2
dataContract.sourceProfile = WORKFORCE_DEPLOYMENT_V2
```

No new dataset type, IndexedDB store, schema migration, repository migration, or storage-version increment is permitted.

## 4. Workforce Deployment v2 UI contract

Selecting Workforce Deployment v2 must show this schema before file upload:

| Required headers | Optional headers |
| --- | --- |
| `EMPLOYEE ID` | `VALID TO` |
| `BANK ID` | |
| `BRANCH CODE` | |
| `DEPLOYMENT TYPE` | |
| `VALID FROM` | |

Help text must state that the master records effective-dated employee-to-branch deployment. `DEPLOYMENT TYPE` is `PRIMARY` or `SUPPORT`; neither type establishes premium ownership, RM identity, a manager, or a business-attribution share.

The existing native authority remains the sole validator:

```text
BancaTrackerWorkforceDeployment
```

The UI must not copy, weaken, or reimplement the authority’s validation rules.

## 5. Legacy Branch Assignment UI contract

Branch Assignment remains separately selectable and retains its existing schema:

| Required headers | Optional headers |
| --- | --- |
| `BANK ID` | `VALID FROM` |
| `BRANCH CODE` | `VALID TO` |
| `RM ID` | |
| `ACTIVE` | |

The existing legacy authority remains the sole validator:

```text
BancaTrackerBranchAssignmentMaster
```

`ASSIGNMENT_EMPLOYEE_NOT_RM` and the underlying `ROLE = RM` requirement remain unchanged. Native non-RM deployment eligibility must not change this legacy rule.

## 6. Routing and contract firewall

The existing import route determines the profile from headers:

```text
DEPLOYMENT TYPE present → Workforce Deployment v2
RM ID present          → Legacy Branch Assignment
both present           → WORKFORCE_DEPLOYMENT_MIXED_CONTRACT_PROHIBITED
```

Native rows must be prepared by `BancaTrackerWorkforceDeployment`; legacy rows must be prepared by `BancaTrackerBranchAssignmentMaster`. Native records must not be translated into legacy rows. Existing profile detection, staging, preflight, activation, metadata creation, persistence, and replacement behavior are retained.

`masterDataImport.js` may change only if a narrow UI alias/schema-routing adaptation is proven necessary. Any such change must preserve the canonical dataset type and every existing profile-dispatch behavior.

## 7. Profile-aware active status

Master Data status rendering must inspect active dataset metadata, not merely dataset type:

| Active metadata profile | Required displayed identity |
| --- | --- |
| `WORKFORCE_DEPLOYMENT_V2` | Workforce Deployment v2 |
| `LEGACY_V1` or metadata-less legacy compatibility | Branch Assignment (Legacy) |

Existing lifecycle information remains visible: active state, dataset identity where currently shown, filename, upload timestamp, and row count.

## 8. Replacement, persistence, and resolver isolation

The existing atomic replacement behavior is mandatory. A failed native preview, preflight, or activation must not replace the previous active dataset. v8.3.1 adds no active-master clear/delete control.

Native records continue to be read only through:

```text
getActiveWorkforceDeploymentContext()
getActiveWorkforceDeploymentResolutionContext(asOfDate)
BancaTrackerWorkforceDeploymentResolver
```

They must remain isolated from legacy `getActiveMasterRecords("BRANCH_ASSIGNMENT")` and the legacy RM resolver. No PRIMARY/SUPPORT record may be projected into an RM assignment or business ownership result.

## 9. Acceptance contract

The corrective implementation is acceptable only when all of the following are proven:

1. Workforce Deployment v2 is explicitly selectable.
2. Native required/optional schema help is visible before file upload.
3. Valid native data activates through `BancaTrackerWorkforceDeployment`.
4. A valid native non-RM employee is accepted.
5. Active native status is labelled Workforce Deployment v2.
6. Native data remains available after reload.
7. Native temporal resolution remains available and correct.
8. Native data does not leak into legacy RM-assignment reads.
9. Mixed native/legacy CSV remains rejected.
10. Invalid native replacement preserves the earlier active data.
11. Branch Assignment (Legacy) remains selectable.
12. Its schema remains unchanged.
13. A legacy non-RM employee remains rejected with `ASSIGNMENT_EMPLOYEE_NOT_RM`.
14. Existing generic Master Data status, preview, activation, and replacement behavior remains intact.

## 10. Permitted implementation surface

Expected files:

```text
js/masterDataAdmin.js
focused Master Data UI/import tests
```

Conditionally permitted:

```text
js/masterDataImport.js
```

It may change only for a narrow UI alias/schema-routing adaptation that cannot safely live in Master Data Administration alone.

Protected unless a concrete integration blocker is demonstrated:

```text
js/masters/workforceDeployment.js
js/masters/branchAssignmentMaster.js
js/enrichment/assignmentResolver.js
js/enrichment/workforceDeploymentResolver.js
js/data/repository.js
js/data/indexedDbAdapter.js
js/data/schema.js
js/data/datasetRegistry.js
business attribution, hierarchy, enrichment, and analytics modules
```

## 11. Explicit exclusions

This corrective release must not introduce workforce-architecture redesign, a new dataset/store/schema, repository changes, IndexedDB changes, Employee/Branch/Hierarchy changes, attribution or ownership semantics, analytics/UI expansion beyond Master Data exposure, migration, active-master deletion, template/download functionality, or unrelated refactoring.

## 12. Patch principle

v8.3.1 must use the smallest patch that makes the existing native authority discoverable and correctly described. It must not consolidate the two authorities, rename persistence identities, or repurpose legacy validation.
