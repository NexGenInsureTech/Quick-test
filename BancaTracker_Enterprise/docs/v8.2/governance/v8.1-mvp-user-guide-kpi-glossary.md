# BancaTracker Enterprise v8.1.0

## MVP User Guide, KPI Glossary & Interpretation Baseline

**Document status:** v8.2 Architecture Baseline
**Reference application:** BancaTracker Enterprise v8.1.0
**Release baseline:** `v8.1.0`
**Purpose:** Freeze the meaning and interpretation of the released MVP before v8.2 changes its data architecture.

---

# 1. Purpose of This Document

This document serves three purposes:

1. provide a practical guide for users of BancaTracker Enterprise v8.1.0;
2. define the meaning of important KPIs, terms, tables and management cues;
3. establish the **semantic baseline** against which v8.2 changes will be assessed.

The objective is important:

> v8.2 may change how data is stored, enriched, mapped and resolved, but it must not accidentally change what an existing v8.1 KPI means.

Where v8.2 intentionally changes a definition, that change must be documented as a deliberate semantic change rather than emerging accidentally from implementation.

---

# 2. What BancaTracker Enterprise Is

BancaTracker Enterprise is an offline browser-based Bancassurance management and analytics application.

The v8.1 MVP converts uploaded policy/premium data into management views covering areas such as:

- business performance;
- branch activation;
- partner-bank performance;
- RM and branch productivity;
- management scorecards;
- data quality;
- management priorities and action cues.

The application is intended to answer not only:

> “How much premium did we write?”

but progressively:

> “Where did it come from?”

> “How broad is participation?”

> “Which bank, branch or RM needs attention?”

> “Can management trust the underlying data?”

---

# 3. v8.1.0 Data Philosophy

In v8.1.0, the uploaded PR dataset is the principal analytical source.

The uploaded data contains transaction information together with several reporting/reference fields.

Certain fields such as:

- Month;
- Day;
- Zone;

may have been derived externally in Excel before upload.

That is valid behavior for the frozen v8.1.0 release.

From v8.2 onward, some of those derived/reference responsibilities will move into BancaTracker itself.

This document, however, describes **v8.1.0 semantics** unless explicitly stated otherwise.

The normal MVP workflow is:

```text
Open BancaTracker

        ↓
Allow processing and validation

Review the reporting period
        ↓

        ↓
Review Performance
        ↓

        ↓

        ↓
```

A recommended management habit is:

> **Trust the data first, interpret performance second.**

If significant Data Quality warnings exist, management conclusions should be treated with appropriate caution.

# 5. Current Period

## Definition

**Current Period** refers to the reporting period BancaTracker currently considers active for the relevant analysis.

In the released v8.1 architecture, period interpretation is centralized rather than allowing each dashboard to invent its own definition.

The latest configured/available reporting period normally drives the current-period analytical context.

## Why It Matters

Metrics such as:

- current-period premium;
- contribution;
- activation;
- productivity;
- priority;

must use consistent time scope.

Otherwise two pages could display apparently conflicting numbers while both technically use different periods.

## Interpretation

When reading any KPI, users should mentally ask:

> “For which period is this being calculated?”

v8.1.0 was specifically improved to make this scope more consistent across modules.

---

# 6. Performance MIS

## Purpose

The Performance MIS provides the central view of business production under the currently applied filters.

It helps answer:

- How much business was generated?
- Which bank or organisational unit generated it?
- Where is contribution concentrated?
- Which portions of the network are producing little or no business?
- What happens when the reporting population is filtered?

## Interpretation Principle

Performance should not be read only as an absolute premium number.

Management should consider:

```text
Premium
+
Contribution
+
Network breadth
+
Activation
+
Productivity
+
Data Quality
```

A high-premium unit with narrow participation may require a different management response from a similarly sized unit with broad participation.

# 7. Premium

## Definition

Premium represents the premium value present in the uploaded PR transactions included in the active analytical scope.

## Important v8.1 Behavior

v8.1.0 explicitly distinguishes:

- positive premium records;
- zero-premium records;
- negative premium records.

Negative premium is therefore not silently converted to zero or discarded.

## Interpretation

### Positive Premium

Represents positive production within the supplied dataset.

### Zero Premium

Represents records whose premium value is numerically zero.

Zero is a genuine value and must not be confused with missing data.

### Negative Premium

Can arise from reversals, cancellations, endorsements or other source-system adjustments.

Negative premium should therefore be visible to management and Data Quality rather than silently hidden.

# 8. Contribution %

## Definition

Contribution % expresses the share of the selected total premium attributable to a particular analytical unit.

Conceptually:

```text
Contribution %
=
Unit Premium
÷
Total Premium in Current Analytical Scope
× 100
```

## Example

If total selected premium is ₹100 crore and Bank A contributes ₹35 crore:

```text
Contribution = 35%
```

## Interpretation

Contribution answers:

> “How important is this unit to the total result?”

It does **not** answer:

> “Is this unit performing well against its potential or budget?”

A large bank can have high contribution but poor penetration.

A smaller bank can have low contribution but excellent execution.

---

# 9. Branch Universe

## Definition

Branch Universe represents the configured population of branches against which branch participation/activation is assessed.

It is conceptually different from branches merely seen in the uploaded transaction data.

## Why This Matters

Suppose a bank has:

```text
1,000 configured branches
```

but transactions appear from only:

```text
300 branches
```

Looking only at transaction records would hide the remaining 700 branches.

The Branch Universe provides the denominator needed for meaningful activation analysis.

---

# 10. Observed Branch

## Definition

An **Observed Branch** is a branch identity that appears in the uploaded transaction data for the relevant analytical scope.

Observed does not automatically mean active.

## Interpretation

Observed answers:

> “Did this branch appear in the supplied data?”

It does not necessarily answer:

> “Did this branch produce enough qualifying business to count as activated?”

---

# 11. Active Branch

## Definition

An **Active Branch** is a branch that meets the application's qualifying activity criteria for the relevant scope.

Conceptually:

```text
Observed Branch
+
qualifying premium/activity condition
=
Active Branch
```

The exact qualifying threshold is implementation/configuration-defined and must be source-code verified before this definition is converted into a permanently published numeric threshold.

## Interpretation

Active Branch answers:

> “How much of our intended distribution network is genuinely producing?”

---

# 12. Near-Active Branch

## Definition

A **Near-Active Branch** is an observed branch whose activity falls below the qualifying activation threshold but is sufficiently close to that threshold to merit management attention.

Its purpose is operational rather than merely descriptive.

Near-active branches are intended to identify:

> “Where is the shortest path to increasing activation?”

The exact v8.1 numeric threshold/band must remain sourced from the released implementation rather than being recreated from memory.

## Management Interpretation

Near-active branches can often be more actionable than completely dormant branches.

For example:

```text
Dormant branch
→ may require full engagement

Near-active branch
→ may require only one additional case / incremental premium
```

---

# 13. Activation %

## Definition

Conceptually:

```text
Activation %
=
Active Branches
÷
Branch Universe
× 100
```

## Example

If:

```text
Branch Universe = 1,000
Active Branches = 420
```

then:

```text
Activation = 42%
```

## Interpretation

Activation measures **distribution breadth**, not simply premium volume.

Two banks could generate identical premium:

```text
Bank A: ₹50 Cr from 700 active branches
Bank B: ₹50 Cr from 150 active branches
```

Their business concentration and execution profile are very different.

---

# 14. Activation Gap

## Definition

Activation Gap represents the difference between the configured branch universe and the currently active branch population.

Conceptually:

```text
Activation Gap
=
Branch Universe
-
Active Branches
```

## Interpretation

The number describes the remaining network opportunity from an activation perspective.

It does not mean that every inactive branch has equal potential.

Future versions may combine activation gap with branch potential, productivity and management hierarchy.

---

# 15. Observed BA Codes

## Definition

**Observed BA Codes** refers to distinct BA Codes detected in the uploaded transaction dataset within the relevant analytical scope.

The terminology intentionally uses **Observed** because the measure reflects what is present in transaction data rather than asserting that it represents the complete configured universe.

## Interpretation

This is a data-observation metric.

It should not automatically be interpreted as:

- total branches;
- total mapped branches;
- total authorised codes;
- total active network.

---

# 16. IMD Count

## Definition

IMD Count represents distinct IMD identities observed within the active analytical population, according to the application's normalized IMD field.

## Interpretation

It measures observed intermediary breadth.

It must be interpreted alongside Data Quality because inconsistent IMD mappings can inflate or fragment apparent counts.

---

# 17. RM Count

## Definition

RM Count represents distinct RM identities observed/resolved within the relevant analytical scope.

## Interpretation

RM counts are sensitive to mapping consistency.

Examples of problematic source data include:

```text
same RM with multiple names
same BA Code mapped to multiple RMs
blank RM identifiers
```

These are therefore not merely cosmetic data issues—they can affect productivity analysis.

---

# 18. Productivity

## Definition

Productivity measures output relative to a defined producing unit.

v8.1.0 includes productivity analysis across levels such as:

- RM;
- IMD;
- Branch.

Typical productivity measures include:

```text
Premium per RM
Premium per IMD
Premium per Branch
Premium per Active Branch
Premium per Observed Branch
```

depending on the specific card/table.

## Interpretation

Productivity should always be read together with the denominator.

For example:

```text
₹10 lakh per Active Branch
```

and

```text
₹10 lakh per Observed Branch
```

are not necessarily the same KPI.

---

# 19. Breadth

## Definition

Breadth describes the spread of business across the relevant organisational/network population.

Examples include:

- number of branches producing;
- number of RMs observed;
- number of IMDs observed;
- product breadth.

## Interpretation

Broad participation typically indicates greater distribution resilience than business concentrated in a small number of units.

However, breadth alone does not prove profitability, quality or sustainability.

---

# 20. Management Scorecard

## Purpose

The Management Scorecard consolidates multiple dimensions into an executive view of partner-bank performance and management attention.

v8.1.0 enhancements include measures such as:

- current-period premium;
- contribution;
- observed branches;
- active branches;
- branch universe;
- activation %;
- near-active branches;
- aggregate activation gap;
- BA / IMD counts;
- Data Quality status;
- priority classification.

## Interpretation

The Scorecard should be read horizontally rather than by one metric.

A partner may show:

```text
High Premium
+
Low Activation
+
High Contribution
+
Poor Data Quality
```

That describes a very different situation from:

```text
Moderate Premium
+
Strong Activation
+
Broad Participation
+
Good Data Quality
```

---

# 21. Partner Scorecard

## Definition

The Partner Scorecard provides one comparative row/view for each configured partner bank.

v8.1.0 intentionally preserves partner visibility even when a bank has zero business in the current scope.

## Why Zero Rows Matter

A bank with no current-period business should not disappear.

Disappearance can falsely imply:

> “This partner is not part of the universe.”

Instead, a visible zero row allows management to recognize:

> “This configured partner currently has no observed production.”

---

# 22. Unconfigured Bank

## Definition

An **Unconfigured Bank** is a bank identity found in transaction data that does not map to the application's known/configured partner-bank definitions.

v8.1.0 specifically improved handling so these records remain visible in the `ALL` view rather than disappearing.

## Priority

Unknown/unconfigured banks are classified as:

```text
UNCONFIGURED
```

where applicable.

## Interpretation

This is primarily a configuration/data-governance issue.

It should not automatically be treated as business underperformance.

---

# 23. Priority Classification

## Purpose

Priority classification converts multiple observed metrics into a management-attention cue.

The purpose is:

> “Where should management look first?”

rather than:

> “Which partner is objectively good or bad?”

## Interpretation

Priority rules should be read together with their explanation.

A priority may result from combinations of:

- business scale;
- activation;
- participation gap;
- contribution;
- Data Quality;
- absence of production;
- configuration status.

The exact rule ordering and thresholds remain defined by the released v8.1 implementation and should be source-verified before publishing numeric decision boundaries.

---

# 24. Management Actions

## Purpose

Management Actions convert analytical observations into operational cues.

They are intended to help users move from:

```text
What happened?
```

to:

```text
Where should I investigate or intervene?
```

They are management prompts, not automated business decisions.

Users should still apply:

- local context;
- partner knowledge;
- seasonality;
- portfolio considerations;
- operational circumstances.

---

# 25. Data Quality Page

## Purpose

The Data Quality page evaluates whether the uploaded information is sufficiently coherent for reliable management analysis.

v8.1.0 checks areas including:

- Zone conflicts;
- State conflicts;
- IMD conflicts;
- BA Code ↔ RM multi-mapping;
- Product Code ↔ Product Name multi-mapping;
- configured months vs absent months;
- unknown banks;
- positive / zero / negative premium counts;
- optional-field completeness;
- exact duplicate records;
- observed values exceeding configured universes.

---

# 26. Mapping Conflict

## Definition

A mapping conflict exists when one supposedly stable business identifier maps inconsistently to multiple descriptive or organisational values.

Example:

```text
BA001 → RM A
BA001 → RM B
```

or:

```text
Product Code 123 → Product X
Product Code 123 → Product Y
```

## Interpretation

A mapping conflict does not automatically prove that either row is wrong.

It means the dataset cannot safely assume a one-to-one relationship.

---

# 27. Multi-Mapping

## Definition

Multi-mapping occurs when a single identifier is associated with multiple values where the analytical model expects greater stability.

Examples:

```text
BA Code → multiple RMs

Product Code → multiple Product Names
```

## Why It Matters

Multi-mapping can distort:

- RM productivity;
- branch ownership;
- product aggregation;
- scorecards;
- drill-down results.

---

# 28. Exact Duplicate

## Definition

An exact duplicate is a record whose relevant uploaded values duplicate another record according to the application's duplicate-detection logic.

## Interpretation

A duplicate is a Data Quality signal, not automatically proof of erroneous business.

Some source systems may legitimately export multiple apparently identical rows.

Therefore duplicates should be reviewed before deletion.

---

# 29. Optional Field Completeness

## Definition

Optional Field Completeness measures the degree to which analytically useful but non-mandatory fields are populated.

## Interpretation

A PR file can be technically valid while still having weak analytical richness.

For example:

```text
Premium present       ✓
Policy date present   ✓
Product present       ✓
RM missing            !
Branch missing        !
```

The dataset may support total premium reporting but weaken RM or branch analytics.

---

# 30. Configured Month vs Observed Month

## Configured Month

A reporting month known/configured in application logic or expected reporting scope.

## Observed Month

A month actually detected in uploaded transactions.

## Interpretation

Differences can indicate:

- source-file incompleteness;
- upload of the wrong period;
- missing production;
- date-format problems;
- legitimate zero-business periods.

---

# 31. Observed Greater Than Universe

## Definition

This Data Quality condition occurs when an observed population exceeds the configured population that should logically contain it.

Example:

```text
Configured Branch Universe = 500
Observed distinct branches = 540
```

## Interpretation

This normally requires investigation of:

- branch identity duplication;
- unmapped codes;
- stale configuration;
- incorrect universe;
- cross-bank contamination;
- source-system inconsistencies.

BancaTracker should surface rather than hide this inconsistency.

---

# 32. Data Quality Status

## Purpose

Data Quality Status provides a management-level summary of whether identified quality conditions warrant attention.

## Interpretation

A Data Quality warning means:

> “Interpret the affected analytics with caution.”

It does not necessarily mean:

> “The entire dataset is unusable.”

The affected dimensions and severity should be considered.

---

# 33. Positive / Zero / Negative Record Counts

These counts describe the distribution of transaction rows by premium sign.

Conceptually:

```text
Positive > 0
Zero      = 0
Negative < 0
```

They provide a fast diagnostic of transaction composition.

They should not be interpreted as policy counts unless each row is known to represent exactly one policy.

---

# 34. Filters

## Purpose

Filters narrow the analytical population.

Common filter dimensions may include:

- partner bank;
- period/month;
- other configured analytical dimensions.

## Core Semantic Rule

When filters are applied:

> KPI numerators and denominators must be recalculated consistently for that filtered analytical scope.

A filter should not produce a premium from one population while leaving its contribution or activation denominator anchored to an unrelated population unless explicitly designed that way.

---

# 35. `ALL` View

## Definition

`ALL` represents the combined analytical population covered by the relevant module.

v8.1.0 specifically ensures that unknown/unconfigured-bank transactions remain represented appropriately rather than making totals silently fail to reconcile.

## Important Check

Partner contributions in the full view should reconcile to:

```text
100%
```

subject to normal numeric rounding.

---

# 36. Drill-Down

## Purpose

Drill-down enables users to move from a high-level KPI into the underlying contributor population.

For example:

```text
Bank
 ↓
RM / IMD / Branch
 ↓
Underlying records or contributor metrics
```

## Interpretation

Drill-down is intended to answer:

> “What is driving this number?”

not merely reproduce the summary card.

# 38. Common Interpretation Mistakes

## Mistake 1 — High Premium Means Strong Network

Not necessarily.

High premium may be concentrated in very few branches.

Always consider activation and breadth.

---

## Mistake 2 — Observed Means Active

Not necessarily.

A branch can appear in data without satisfying activation criteria.

---

## Mistake 3 — Missing Means Zero

Incorrect.

```text
null / missing ≠ 0
```

Zero is a real numeric value.

---

## Mistake 4 — Unknown Bank Means Zero Business

Incorrect.

An unknown bank may carry premium but lack configuration.

---

## Mistake 5 — Contribution Means Achievement

Incorrect.

Contribution answers:

> “What share of total?”

Achievement requires a target/budget denominator, which is a separate concept.

---

## Mistake 6 — Productivity Means Total Premium

Incorrect.

Productivity always requires a denominator.

---

## Mistake 7 — Data Quality Warning Means Discard Everything

Not necessarily.

The warning may affect only a specific dimension.

# 39. Current v8.1 Limitations That v8.2 Will Address

The following are known architectural boundaries rather than errors in v8.1.0.

### Externally Derived Date Fields

Month and Day may currently be prepared in Excel.

v8.2 will derive them internally from `POLICY ISSUED DATE`.

### Externally Derived Zone

Zone may currently depend on State-to-Zone VLOOKUP preparation.

v8.2 will resolve geography internally.

### Branch Identity

v8.1 relies substantially on information present in transaction data/configuration.

v8.2 will introduce a durable Branch Master.

### Organisation Structure

v8.2 will introduce persistent:

```text
National Head
→ ZSM
→ ASM
→ CSM
→ RM
```

hierarchy.

### Budget and Potential

v8.2 will introduce branch-level Budget and Potential master data.

### Persistent Reference Data

v8.2 will introduce persistent browser-local master datasets.

### Day-wise Comparison

Future versions will support:

```text
Month A vs Month B
Daily Premium
Cumulative Premium
Growth / Degrowth
Run-rate
```

# 40. Semantic Preservation Rules for v8.2

The following rules must guide implementation.

## Rule 1

Moving Month derivation from Excel to JavaScript must not silently change what a reporting month means.

## Rule 2

Moving Zone resolution to Geography Master must not silently change Zone aggregation without a documented mapping change.

## Rule 3

Introducing Branch Master must distinguish:

```text
Observed branch
Configured branch
Active branch
```

rather than merging those concepts.

## Rule 4

Introducing hierarchy must not cause historical transactions to be reinterpreted under current management structures without an explicit effective-date policy.

## Rule 5

Adding Budget must introduce a new concept:

```text
Achievement
```

without redefining:

```text
Contribution
```

## Rule 6

Adding Potential must introduce:

```text
Penetration / Opportunity
```

without conflating it with Budget.

## Rule 7

A Data Quality issue should become more explainable under v8.2, never less visible.

# 43. Semantic Change Control

From v8.2 onward, any KPI definition change should be classified as one of:

### IMPLEMENTATION CHANGE

The calculation mechanism changes, but business meaning does not.

Example:

```text
Month derived internally instead of supplied by Excel
```

### DATA SOURCE CHANGE

The authoritative source changes.

Example:

```text
Zone now resolved from Geography Master
```

### SEMANTIC CHANGE

The business meaning or formula changes.

Example:

```text
Activation threshold changes
```

Semantic changes should require explicit documentation and regression review.
