# BancaTracker Enterprise v8.2

## Step 1C — Persistence & Master Data Architecture

**Status:** Architecture Design
**Branch:** `feature/v8.2-data-foundation`
**Production baseline:** v8.1.0 frozen
**Implementation:** Not started

---

# 1. Objective

v8.2 requires persistent browser-local master/reference datasets that:

- survive browser refresh and application restart;
- remain available until deliberately replaced;
- support larger structured datasets than `localStorage`;
- do not directly couple dashboards to browser storage;
- protect the currently active master when a replacement upload fails;
- provide metadata showing which dataset is currently active;
- support future schema migration and historical/effective-date relationships.

The architectural target is:

```text
UI / Dashboard
      ↓
Analytics
      ↓
Resolvers / Enrichment
      ↓
Repository API
      ↓
IndexedDB Adapter
      ↓
Browser IndexedDB
```

No dashboard or analytics module should access IndexedDB directly.

---

# 2. Persistence Technology Decision

The primary persistence technology for v8.2 master/reference data will be:

**IndexedDB**

Use `localStorage` only for small application preferences such as:

- theme;
- selected page;
- display preferences;
- possibly last-used filters.

Do not use `localStorage` for:

- Branch Master;
- Geography Master;
- hierarchy;
- branch assignments;
- Budget;
- Potential;
- Product Master;
- large transaction datasets.

---

# 3. Why IndexedDB

IndexedDB is preferred because it provides:

- significantly larger practical storage capacity;
- structured object storage;
- indexed lookups;
- transactions;
- asynchronous APIs;
- offline operation;
- browser-native support;
- better scalability for thousands of master records.

This fits the existing offline HTML/CSS/Vanilla JavaScript architecture without introducing an external database or server dependency.

---

# 4. Database Boundary

Recommended database name:

```text
bancatracker-enterprise
```

Recommended initial schema version:

```text
1
```

Conceptually:

```javascript
const DB_NAME = "bancatracker-enterprise";
const DB_VERSION = 1;
```

The database version is a **storage schema version**, not the BancaTracker product version.

For example:

```text
Application version: v8.2.0
IndexedDB schema:    1
```

These must remain separate concepts.

---

# 5. Storage Philosophy

Do not create one IndexedDB database per master.

Use one application database containing logically separated stores.

Conceptually:

```text
bancatracker-enterprise
│
├── datasets
├── branchMaster
├── geographyMaster
├── employeeMaster
├── hierarchyRelationships
├── branchAssignments
├── budgets
├── potentials
├── productMaster
└── appMetadata
```

Transaction persistence may be added separately after its lifecycle and scale are explicitly designed.

Step 1C primarily concerns persistent master/reference datasets.

```text
datasetId
```

```text

```

---

# 7. Dataset Status Model

Recommended statuses:

```text
STAGED
ACTIVE
SUPERSEDED
FAILED
```

Meaning:

### STAGED

Parsed and validated data awaiting activation.

### ACTIVE

The dataset currently used by the application.

### SUPERSEDED

A previously active dataset replaced by a newer one.

### FAILED

An upload/import attempt that could not become active.

The application should have **only one ACTIVE dataset per dataset type**.

# 9. Why Records Carry `datasetId`

Master rows should not simply overwrite previous rows during staging.

Instead:

```text
Dataset Version 3
    branch records

Dataset Version 4
    branch records
```

can temporarily coexist.

Only when Dataset Version 4 is successfully activated does it become authoritative.

This enables safe replacement.

# 18. Active Dataset Pointer Principle

Do not determine the active dataset by:

```text
highest version number
```

or:

```text
latest uploaded timestamp
```

Instead, maintain an explicit active pointer.

Example:

```text
BRANCH_MASTER
      ↓
BRANCH_MASTER:4
```

This provides controlled activation and future rollback capability.

---

# 19. Safe Replacement Strategy

This is the most important part of Step 1C.

A replacement upload should follow:

```text
Current ACTIVE dataset
        │
        │ remains untouched
        ▼

Upload new file
        ↓
Parse
        ↓
Normalize
        ↓
Validate schema
        ↓
Validate records
        ↓
Validate references
        ↓
Create STAGED dataset
        ↓
Write staged records
        ↓
Verify staged write
        ↓
Activate new dataset
        ↓
Mark old ACTIVE → SUPERSEDED
        ↓
Update active pointer
```

At no point before activation should the previous active dataset be destroyed.

---

# 20. Atomic Activation

The critical activation operations should occur in a single IndexedDB transaction wherever practical.

Conceptually:

```text
Begin transaction
    ↓
old dataset:
ACTIVE → SUPERSEDED
    ↓
new dataset:
STAGED → ACTIVE
    ↓
update active pointer
    ↓
commit
```

If any operation fails:

```text
transaction aborts
```

and the previous active state remains intact.

This is the central protection against partial master replacement.

---

# 21. Failed Upload Rule

The invariant is:

> **A failed upload must never affect the currently active dataset.**

Examples:

- malformed CSV;
- missing required field;
- duplicate branch identity;
- invalid hierarchy;
- broken reference;
- storage error;
- validation exception.

All must leave the previous active dataset operational.

---

# 22. Staging Strategy

A new dataset should be fully written under its new `datasetId`.

Example:

```text
Current:
BRANCH_MASTER:4 → ACTIVE

New upload:
BRANCH_MASTER:5 → STAGED
```

Only after successful verification:

```text
BRANCH_MASTER:4 → SUPERSEDED
BRANCH_MASTER:5 → ACTIVE
```

This eliminates destructive replacement.

---

# 23. Cleanup Policy

Do not immediately delete the superseded dataset.

Initially retain:

```text
current ACTIVE version
+
at least one previous SUPERSEDED version
```

This provides simple rollback protection during v8.2 development.

Future storage-management policy can define how many historical versions to retain.

A reasonable future default might be:

```text
ACTIVE + previous 2 versions
```

but this should remain configurable rather than being hard-coded during Step 1C.

---

# 24. Rollback Architecture

Because older datasets remain stored, future rollback can conceptually perform:

```text
Current:
BRANCH_MASTER:5 ACTIVE

Rollback requested
        ↓
BRANCH_MASTER:5 SUPERSEDED
BRANCH_MASTER:4 ACTIVE
        ↓
active pointer → BRANCH_MASTER:4
```

Rollback does not need to be exposed in the first v8.2 UI.

However, the persistence design should allow it.

---

# 28. Repository Responsibility

The repository should know:

- which dataset is active;
- where its records are stored;
- how to retrieve them;
- how to stage replacements;
- how to activate datasets;
- how to expose metadata.

The repository should **not** know:

- how activation % is calculated;
- how premium is aggregated;
- how dashboards render cards;
- which KPI is red or green.

Those belong elsewhere.

---

# 29. Resolver Responsibility

Similarly, persistence should not perform business enrichment.

For example:

```text
Repository
    ↓
returns Branch Master
```

Then:

```text
BranchResolver
    ↓
resolves transaction → branch
```

This is preferable to:

```text
IndexedDB code
    ↓
attempts to resolve business relationships
```

Persistence and business semantics must remain separate.

---

# 30. Read Strategy

Master datasets should not necessarily perform an IndexedDB lookup for every PR transaction.

For analytics performance, the preferred pattern is:

```text
Load active master once
        ↓
construct in-memory lookup maps
        ↓
resolve many transaction records
```

For example:

```javascript
branchByKey.get("IB:12345");
```

rather than performing thousands of IndexedDB operations.

IndexedDB provides persistence.

In-memory maps provide analytical speed.

---

# 32. Cache Invalidation Rule

When:

```text
Branch Master v4
```

is replaced by:

```text
Branch Master v5
```

the application must not continue using an old in-memory branch map.

Therefore activation should generate an internal event such as:

```text
DATASET_ACTIVATED
```

or explicitly call:

```text
MasterDataCache.invalidate("BRANCH_MASTER")
```

The exact mechanism will be designed during implementation.

Conceptually:

```text
Bank Configuration
       │
       ├──── Geography Master
       │
       ▼
Branch Master
       │
       ├──── Branch Assignment
       │
```


---

# 34. Dependency-Aware Replacement

Suppose Branch Master changes.

Existing:

```text
Branch Assignment
Budget
Potential
```

may now refer to branch IDs that no longer exist.

Therefore activating a replacement Branch Master should trigger cross-dataset validation.

Example:

```text
New Branch Master
       ↓
Check active Branch Assignments
Check active Budget
Check active Potential
       ↓
Show impact
```

If the new Branch Master would orphan important references, activation should either:

- block with an ERROR; or
- require explicit resolution depending on severity.

For the first implementation, serious referential breakage should block activation.

---

# 35. Dependency Validation Examples

### Geography replacement

Check:

```text
Does every active Branch Master stateId still exist?
```

### Employee replacement

Check:

```text
Do all hierarchy employees still exist?
Do all assigned RMs still exist?
```

### Branch replacement

Check:

```text
Do all assignments still resolve?
Do all budget records still resolve?
Do all potential records still resolve?
```

---

# 36. Full Replacement vs Merge

v8.2 initial master management will use:

**Validated full replacement**

not row-level incremental merge.

Example:

```text
New Branch Master file
=
proposed complete Branch Master
```

This simplifies:

- stale-record handling;
- deletion semantics;
- duplicate detection;
- validation;
- rollback;
- auditing.

Incremental merge/upsert can be considered in a later version.

---

# 37. Dataset Version Numbers

Dataset versions are independent for each dataset type.

Example:

```text
BRANCH_MASTER      v4
GEOGRAPHY_MASTER   v2
EMPLOYEE_MASTER    v6
BUDGET              v8
```

There is no requirement that all masters share a common version.

---

# 38. Application Schema Migration

IndexedDB uses an integer DB schema version.

Example:

```text
DB_VERSION = 1
```

A future structural change may require:

```text
DB_VERSION = 2
```

The upgrade path should be handled through explicit migrations.

Conceptually:

```text
DB v1
  ↓
migration
  ↓
DB v2
```

Never delete the database simply because the schema changes.

---

# 39. Migration Rules

Every storage migration should aim to be:

- deterministic;
- forward-only during normal upgrades;
- testable;
- non-destructive;
- idempotent where practical.

For example:

```text
Migration 1 → 2
Add index to branchMaster
```

should not rewrite unrelated stores.

---

# 40. No Automatic Database Reset

The application must never respond to an IndexedDB schema mismatch by silently executing:

```text
deleteDatabase()
```

Persistent master data is business data.

Any destructive reset must be an explicit administrative action.

---

# 41. Storage Failure Handling

Possible browser storage problems include:

- quota exceeded;
- transaction abort;
- unavailable IndexedDB;
- browser privacy restrictions;
- write failure;
- corrupted/stale transaction state.

The application should display a clear error and preserve existing active data wherever possible.

Never treat a failed persistence write as successful simply because parsing succeeded.

---

# 44. Source File Retention

The system does not need to persist the entire uploaded CSV file as a binary object for the first version.

Persist:

```text
file name
dataset metadata
normalized records
validation summary
```

rather than retaining duplicate raw files unnecessarily.

Future provenance requirements may justify retaining raw-file fingerprints/checksums.

---

# 45. Fingerprinting

A future dataset fingerprint can help identify accidental re-upload of the exact same master.

Conceptually:

```text
SHA-256 normalized dataset fingerprint
```

This is optional for the initial implementation.

It should not block v8.2 foundation work.

# 46. Transaction Data Boundary

Step 1C deliberately does **not yet require permanent PR transaction persistence**.

Current v8.1 behavior should remain stable while master persistence is introduced.

Recommended migration sequence:

```text
v8.1 transaction workflow
          +
persistent v8.2 masters
          ↓
canonical enrichment
          ↓

```

This reduces migration risk.

# 47. v8.1 Isolation Rule

Existing v8.1 modules such as:

```text
performance
activation
scorecard
productivity
data quality
```

must not be rewritten merely to introduce IndexedDB.

Initial persistence work should be additive.

Only after the repository and resolvers are independently tested should existing analytics begin consuming enriched data.

# 48. Feature Detection

Before persistence initialization, the application should verify that IndexedDB is available.

Conceptually:

```javascript

  // show persistence capability error
}
```

```text
      ↓

      ↓

Relationships
      ↓
```

# 50. Master Data Lifecycle

Every master follows:

```text
ABSENT
   ↓
UPLOAD
   ↓
VALIDATE
   ↓
STAGED
   ↓
ACTIVE
   ↓
SUPERSEDED
```

Failure can occur before ACTIVE:

```text
UPLOAD
   ↓
FAILED
```

but must never remove the existing ACTIVE dataset.

---

# 51. First-Run State

A fresh browser may have no persistent masters.

The repository must tolerate:

```text
BRANCH_MASTER = absent
GEOGRAPHY_MASTER = absent
HIERARCHY = absent
```

The application should report:

```text
Not Configured
```

rather than crash.

This is especially important while v8.1 compatibility remains active.

---

# 52. UNMAPPED vs MASTER ABSENT

These must remain distinct.

### MASTER ABSENT

No relevant master is configured.

### UNMAPPED

The master exists, but a particular source value cannot be resolved.

Example:

```text
Geography Master absent
→ geography resolution unavailable
```

versus:

```text
Geography Master active
State "XYZ" not found
→ UNMAPPED
```

This distinction should feed Data Quality.

---

# 53. Persistent Data Backup

A future administration capability should support:

```text
Export Masters
```

into a local backup package.

This is not required for initial Step 1C implementation but should remain architecturally possible.

The repository abstraction makes this easier.

---

# 54. Security and Privacy Boundary

All master data remains:

```text
inside the user's browser profile
```

unless the user deliberately exports it.

No remote service or cloud database is introduced by v8.2 persistence.

Clearing site/browser storage can remove IndexedDB data.

The future user guide should explicitly communicate this limitation.

---

# 55. Recommended Step 1C Architecture Decisions

The following decisions should now be considered locked:

1. IndexedDB is the primary persistent master-data store.
2. `localStorage` remains for small UI preferences only.
3. One BancaTracker IndexedDB database is used.
4. Master datasets are versioned independently.
5. Master records carry a `datasetId`.
6. Active datasets are selected through explicit pointers.
7. Upload replacement uses staging before activation.
8. Existing active data remains untouched until replacement is fully validated.
9. Activation is transactional wherever practical.
10. Failed imports never destroy active datasets.
11. Superseded data is retained temporarily for rollback.
12. Full replacement is preferred over merge for initial v8.2.
13. Repository APIs isolate application logic from IndexedDB.
14. IndexedDB-specific logic lives in a persistence adapter.
15. Resolvers and analytics do not directly access IndexedDB.
16. Active masters may be cached in memory for analytical performance.
17. Cache is invalidated when a master version changes.
18. Master replacements perform dependency validation.
19. Database schema migrations are explicit and non-destructive.
20. Existing v8.1 analytics remain isolated during persistence introduction.
21. Transaction persistence is deferred until separately designed.
22. Missing master and unmapped record are distinct states.
23. Persistent business data must never be silently reset.

# 57. Architecture Decision

> **BancaTracker Enterprise v8.2 will use IndexedDB as an abstracted, versioned and transaction-safe local master-data repository. Master replacements will follow a stage → validate → activate model, ensuring that an invalid or failed upload can never destabilize the currently active dataset or the frozen v8.1 analytical baseline.**
