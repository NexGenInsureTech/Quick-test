# BancaTracker Enterprise v8.2 — Step 1 Architecture Blueprint

## 1. Release Boundary

BancaTracker Enterprise `v8.1.0` is the frozen production baseline.

Development rules for v8.2:

- `main` remains protected as the released v8.1.0 baseline.
- tag `v8.1.0` must never be moved or rewritten.
- all v8.2 work is performed on a separate development branch.
- v8.1.0 behavior must remain reproducible at any time by checking out the release tag.
- v8.2 architecture changes must be additive or safely migratable.
- existing PR upload and analytics capabilities must continue working while new foundations are introduced.

Recommended working branch:

`feature/v8.2-data-foundation`

The branch should be created from the released `main` commit corresponding to `v8.1.0`.

---

# 2. v8.2 Architectural Objective

v8.1 primarily treats uploaded PR data as the source of both transactional information and several reporting dimensions.

v8.2 will introduce a clearer separation between:

### Transaction Data

Policy / premium records uploaded periodically.

Example:

- Policy Number
- Policy Issued Date
- Premium
- Product
- LOB
- BA Code
- Branch Code
- RM identifiers

### Master Data

Relatively stable reference information maintained independently of transactions.

Examples:

- Branch Master
- Organisation Hierarchy
- Geography / Zone Master
- Bank Organisation Mapping
- Product Master
- Budget Master
- Potential Master

### Derived Data

Fields calculated internally by BancaTracker.

Examples:

- Month
- Day
- Zone
- reporting hierarchy
- branch relationships
- budget achievement
- cumulative run-rate
- contribution
- productivity metrics
- management alerts

The target principle is:

**Upload facts once → enrich internally → aggregate consistently → explain transparently.**

The application should evolve toward five logical layers.

```text
┌─────────────────────────────────────────────────────┐
│                    PRESENTATION                      │

                         │
                         ▼

│                ANALYTICS / INTELLIGENCE              │
│ Aggregation • Comparison • Run-rate • Alerts        │
│ Budget • Productivity • Growth / Degrowth           │
└─────────────────────────────────────────────────────┘
                         │
                         ▼
┌─────────────────────────────────────────────────────┐
│                  ENRICHMENT LAYER                    │

                         │
                         ▼
┌─────────────────────────────────────────────────────┐
│                DATA REPOSITORY LAYER                 │

```

UI modules should never need to know whether a field came from the original CSV, a master dataset, or a derived calculation.

They should consume a canonical normalized record.

After ingestion and enrichment, every PR record should conceptually resemble:

```javascript
{
  (transactionId,
    policyNumber,
    policyIssuedDate,
    year,
    month,
    monthKey,
    day,
    premium,
    bankId,
    bankName,
    branchId,
    branchCode,
    branchName,
    stateId,
    stateName,
    zoneId,
    zoneName,
    bankRegionId,
    bankRegionName,
    fgmOfficeId,
    fgmOfficeName,
    rmId,
    rmName,
    csmId,
    csmName,
    asmId,
    asmName,
    zsmId,
    zsmName,
    nationalHeadId,
    nationalHeadName,
    lobId,
    lobName,
    productId,
    productName);
}
```

Not every attribute needs to physically exist on every stored transaction.

Some relationships may be resolved dynamically from master datasets.

But this structure represents the **canonical analytical view** available to the rest of the application.

# 5. Internal Date Derivation

Excel-derived fields should no longer be required.

Given:

`POLICY ISSUED DATE`

BancaTracker derives:

```text
Policy Issued Date
       │
       ├── Year
       ├── Month Number
       ├── Month Label
       ├── Month Key
       └── Day
```

Recommended internal values:

```javascript
year: 2026;
month: 8;
monthLabel: "Aug-26";
monthKey: "2026-08";
day: 24;
```

`monthKey` should be used internally for sorting and comparison.

`monthLabel` is presentation only.

This eliminates problems caused by textual month sorting such as:

```text
Apr-26
Aug-26
Dec-25
Feb-26
```

---

# 6. Geography / Zone Resolution

Zone must no longer depend on an Excel VLOOKUP.

Instead:

```text
Transaction State
        │
        ▼
State / Geography Master
        │
        ├── State
        ├── Zone
        └── optional future geography attributes
```

Recommended conceptual structure:

```javascript
{
  stateId: "IN-AS",
  stateName: "Assam",
  zoneId: "EAST",
  zoneName: "East"
}
```

The transaction enrichment process performs:

```text
STATE → Geography Master → Zone
```

Unknown states must not silently disappear.

They should receive a state such as:

```text
UNMAPPED
```

and appear in Data Quality reporting.

---

# 7. Branch Master

The Branch Master becomes one of the most important datasets in v8.2.

A branch must have a **durable internal identity** independent of display names.

Recommended structure:

```javascript
{
  (branchId,
    bankId,
    branchCode,
    branchName,
    stateId,
    bankRegionId,
    bankZoneId,
    fgmOfficeId,
    status,
    validFrom,
    validTo);
}
```

Primary design rule:

**Branch name must never be the primary key.**

Preferred durable identity:

```text
Bank + Branch Code
```

Example:

```text
IB:12345
IOB:06789
KBL:00421
```

Internally this may become:

```javascript
branchId: "IB-12345";
```

This protects the analytics when:

- branch names change,
- naming conventions differ,
- spelling changes,
- regional assignments change.

---

# 8. Organisation Hierarchy Master

The hierarchy is:

```text
National Head
     │
     ▼
    ZSM
     │
     ▼
    ASM
     │
     ▼
    CSM
     │
     ▼
     RM
```

Recommended principle:

Each person receives a durable ID.

Example:

```javascript
{
  employeeId: "RM00482",
  employeeName: "...",

  role: "RM",

  managerId: "CSM0021",

  validFrom: "2026-04-01",
  validTo: null,

  active: true
}
```

The hierarchy should not be stored solely as repeated names.

Instead:

```text
RM → managerId
CSM → managerId
ASM → managerId
ZSM → managerId
```

This makes hierarchy traversal possible.

---

# 9. Branch-to-RM Relationship

Branch and RM relationships must be handled separately from the organisation hierarchy.

Reason:

An RM can move between territories while remaining under the same or a different management hierarchy.

Therefore we need:

```text
Employee Hierarchy
```

and

```text
Branch Assignment
```

as conceptually separate relationships.

Example:

```javascript
{
  branchId: "IB-12345",
  rmId: "RM00482",

  validFrom: "2026-04-01",
  validTo: null
}
```

This provides the future ability to reconstruct historical ownership correctly.

---

# 10. Budget Architecture

Budget should exist at the lowest useful planning level.

Recommended base level:

```text
Branch + Period
```

Example:

```javascript
{
  branchId: "IB-12345",

  financialYear: "FY2026-27",

  monthKey: "2026-08",

  premiumBudget: 850000,
  potential: 2200000
}
```

From branch-level values BancaTracker can roll upward automatically.

```text
Branch
   ↓
RM
   ↓
CSM
   ↓
ASM
   ↓
ZSM
   ↓
National Head
```

and geographically:

```text
Branch
   ↓
State
   ↓
Zone
   ↓
Bank
```

This prevents maintaining separate budgets for every managerial level.

---

# 11. Monthly vs Annual Budget

The system should support both:

### Annual Budget

```text
Branch + Financial Year
```

and

### Monthly Budget

```text
Branch + Month
```

Preferred rule:

When explicit monthly budget exists, use it.

Otherwise monthly targets may eventually be derived from the annual budget using a distribution profile.

For v8.2 initial architecture:

```text
Explicit Monthly Budget > Derived Monthly Budget
```

The detailed allocation engine can be introduced later.

---

# 12. Potential

Potential must remain distinct from Budget.

```text
Potential ≠ Target ≠ Actual
```

These answer different questions.

### Actual

What business was generated?

### Budget

What business are we expected to generate?

### Potential

What business could realistically exist?

Future intelligence can therefore calculate:

```text
Budget Achievement
Actual / Budget
```

```text
Potential Penetration
Actual / Potential
```

```text
Untapped Potential
Potential - Actual
```

# 13. Persistent Local Master Data

v8.2 requires master/reference datasets to survive browser refresh and application restart.

Conceptual repository:

```text
BancaTracker Local Repository

├── transactionData
├── branchMaster
├── geographyMaster
├── hierarchyMaster
├── branchAssignments
├── budgetMaster
├── potentialMaster
└── metadata
```

The UI should interact through a repository interface rather than accessing browser storage directly.

Conceptually:

```javascript
DataRepository.getBranchMaster();
DataRepository.saveBranchMaster();

DataRepository.getHierarchy();
DataRepository.saveHierarchy();

DataRepository.getBudget();
DataRepository.saveBudget();
```

This isolates persistence technology from application logic.

---

# 14. Persistence Technology

For v8.2 the preferred browser-local persistence mechanism should be:

**IndexedDB**

rather than relying primarily on `localStorage`.

Reasons:

- larger storage capacity,
- better suited to structured datasets,
- asynchronous,
- can handle thousands of branches and reference rows,
- future-friendly for larger datasets,
- still completely browser-local and offline.

`localStorage` can remain appropriate for small UI preferences such as:

```text
selected theme
last dashboard
filter preferences
```

but not enterprise master datasets.

---

# 15. Master Replacement Rule

Master-data uploads should follow a controlled replacement process.

Example:

```text
Upload Branch Master
        │
        ▼
Parse
        │
        ▼
Validate
        │
        ▼
Preview
        │
        ▼
Confirm
        │
        ▼
Replace active Branch Master
```

Never:

```text
Upload → immediately overwrite existing data
```

The current valid dataset should remain available unless the replacement passes validation.

# 16. Dataset Metadata

Every persistent dataset should carry metadata.

Example:

```javascript
{
  datasetType: "branchMaster",
  version: 3,

  uploadedAt: "...",
  rowCount: 13542,

  validRows: 13538,
  invalidRows: 4,

  sourceFile: "branch_master_aug2026.csv"
}
```

This enables future administrative views showing:

- which master is loaded,
- when it was uploaded,
- how many records it contains,
- whether there were validation issues.

# 20. Day-wise Month Comparison Foundation

Once canonical dates exist, future month comparison becomes straightforward.

Example analytical dataset:

```text
Day | Jul-26 | Aug-26 | Growth
--------------------------------
 1  | 1.20Cr | 1.35Cr | +12.5%
 2  | 2.10Cr | 2.31Cr | +10.0%
 3  | 3.40Cr | 3.22Cr | -5.3%
```

Two measures should be available:

### Daily Premium

Business written on that individual calendar day.

### Cumulative Premium

Business written from Day 1 through that day.

Example:

```text
Day 10 cumulative premium
```

allows fair comparison of:

```text
Aug 1–10
vs
Jul 1–10
```

rather than comparing partial August against full July.

# 28. Architecture Principles for v8.2

The following principles should govern all implementation decisions.

### A. Facts and Masters are separate

PR data represents transactions.

Branches, hierarchy, geography and budgets represent reference/master information.

### B. Derive where possible

Do not ask Excel to calculate fields the application can reliably calculate itself.

### C. Stable IDs over names

Names are labels.

IDs are relationships.

### D. Unknown is better than wrong

Missing mappings must surface as `UNMAPPED` or equivalent rather than being silently assigned.

### E. Historical relationships matter

Mappings should eventually allow effective dates.

### F. One dimension model

All dashboards should use the same organisational and geographic definitions.

### G. Persistence is abstracted

Business logic must not depend directly on IndexedDB APIs.

### H. Analytics remain reusable

Calculations belong in analytical modules rather than DOM rendering code.

### I. Explainability is first-class

Every management KPI or generated insight should ultimately be explainable.

### J. v8.1 remains recoverable

No architectural improvement justifies destabilising the released baseline.

# 29. Definition of Done — Step 1

v8.2 Step 1 is complete when we agree that:

- v8.1.0 remains frozen.
- v8.2 uses a separate branch.
- transaction and master data are separate concepts.
- Branch Master has durable branch identity.
- Month and Day will be internally derived.
- Zone will be resolved from master/reference data.
- organisational hierarchy is modeled independently.
- branch assignment is separated from employee hierarchy.
- Budget and Potential are separate measures.
- persistent master data is stored locally.
- IndexedDB is the preferred persistent master-data store.
- dashboards consume canonical enriched data.
- common analytics dimensions will support future roll-ups.
- glossary metadata is centralized.
- future month/day comparison is built on canonical dates and dimensions.
- new architecture is introduced incrementally without destabilizing v8.1.

# Architecture Decision

**BancaTracker Enterprise v8.2 will evolve from an upload-driven dashboard into a locally persistent, master-data-aware analytics platform while retaining its offline HTML/CSS/Vanilla JavaScript architecture.**
