# BancaTracker Enterprise v8.2

## Step 1D — Enrichment & Resolution Pipeline

**Status:** Architecture Design
**Branch:** `feature/v8.2-data-foundation`
**Production baseline:** v8.1.0 frozen
**Implementation:** Not started

---

# 1. Objective

The Enrichment & Resolution Pipeline converts an uploaded PR transaction row into a canonical analytical record.

Its responsibilities are:

- preserve the raw business values needed for audit and Data Quality;
- normalize safely;
- derive internal date fields;
- resolve Bank;
- resolve Branch;
- resolve State and Zone;
- resolve RM;
- traverse the management hierarchy;
- normalize Product and LOB;
- attach provenance and resolution status;
- surface unresolved or conflicting mappings;
- never silently invent business relationships.

The pipeline sits between ingestion and analytics.

```text
Raw PR Data
    ↓
Validation
    ↓
Normalization
    ↓
Enrichment / Resolution
    ↓
Canonical Analytical Record
    ↓
Analytics
    ↓
Dashboards
```

---

# 2. Architectural Position

The pipeline should follow this dependency direction:

```text
PR Upload
   ↓
CSV Processor / Parser
   ↓
Schema Validator
   ↓
Normalizer
   ↓
Enrichment Pipeline
   ↓
Master Data Cache / Resolvers
   ↓
Canonical Records
   ↓
Analytics Modules
```

The enrichment layer must not:

- render DOM;
- calculate dashboard cards;
- store UI state;
- directly manipulate IndexedDB;
- contain presentation labels or HTML.

---

# 3. Central Principle

The core v8.2 rule is:

> **Raw values describe what the source file said. Canonical values describe what BancaTracker has resolved and will use analytically.**

These two concepts must not be confused.

For example:

```text
Uploaded Zone:
South

Resolved Zone:
SOUTH
```

or:

```text
Uploaded Zone:
East

Resolved Zone from State Master:
SOUTH
```

The canonical analytical value is the internally resolved value.

The mismatch becomes a Data Quality finding.

---

# 4. Pipeline Overview

Recommended processing sequence:

```text
1. Receive raw row
        ↓
2. Preserve source values
        ↓
3. Structural validation
        ↓
4. Normalize fields
        ↓
5. Parse POLICY ISSUED DATE
        ↓
6. Derive time dimensions
        ↓
7. Resolve Bank
        ↓
8. Resolve Branch
        ↓
9. Resolve Geography
        ↓
10. Resolve RM Assignment
        ↓
11. Resolve Leadership Hierarchy
        ↓
12. Resolve Product / LOB
        ↓
13. Evaluate legacy field mismatches
        ↓
14. Attach provenance
        ↓
15. Attach Data Quality findings
        ↓
16. Produce canonical analytical record
```

Order matters because later resolution steps depend on earlier ones.

---

# 5. Raw Source Preservation

Before normalization, retain important source values conceptually.

Example:

```javascript
raw: {
  policyNumber: "POL123",
  policyIssuedDate: "24/08/2026",
  bank: "Indian Bank ",
  branchCode: "00123",
  branchName: " GUWAHATI MAIN ",
  state: "Assam",
  zone: "East",
  rmCode: "RM00482",
  rmName: "A Person",
  month: "Aug-26",
  day: "24",
  productCode: "H001",
  productName: "Health Product"
}
```

This does not necessarily mean every raw field must be permanently duplicated in storage.

But the processing layer must retain enough source context to explain:

- what was uploaded;
- what was normalized;
- what was resolved;
- what differed.

---

# 6. Structural Validation

Before enrichment, determine whether the row is structurally processable.

Examples of blocking row errors:

```text
POLICY ISSUED DATE missing
PREMIUM non-numeric
required policy identifier missing
malformed date
```

A structurally invalid row should not continue through ordinary enrichment as if valid.

Recommended row state:

```text
VALID
INVALID
```

A file may contain valid and invalid rows depending on the final upload policy.

The exact file-level rejection threshold can be designed during implementation.

---

# 7. Normalization Layer

Normalization removes technical inconsistencies without changing business meaning.

Examples:

```text
" Indian Bank " → "Indian Bank"
"ASSAM"         → normalized comparison value "ASSAM"
""              → null
```

Potential normalization functions:

```javascript
normalizeText();
normalizeCode();
normalizeBoolean();
normalizePremium();
normalizeDateInput();
normalizeStateName();
normalizeBankName();
```

These functions should be deterministic and reusable.

---

# 8. Code Preservation Rule

Business codes must generally remain strings.

For example:

```text
00123
```

must not automatically become:

```text
123
```

unless the relevant source contract explicitly defines them as equivalent.

This is critical for:

- Branch Codes;
- BA Codes;
- IMD Codes;
- Employee IDs;
- Product Codes.

Excel's tendency to convert identifiers into numbers must not be propagated blindly into the canonical model.

---

# 9. Date Resolution

The authoritative source for reporting date dimensions becomes:

```text
POLICY ISSUED DATE
```

not uploaded `Month` or `Day`.

Example:

```text
POLICY ISSUED DATE = 24/08/2026
```

resolves to:

```javascript
policyIssuedDate: "2026-08-24",
year: 2026,
month: 8,
monthKey: "2026-08",
monthLabel: "Aug-26",
day: 24,
financialYear: "FY2026-27"
```

---

# 10. Date Derivation Rules

The date resolver should derive:

```text
calendar year
calendar month number
monthKey
monthLabel
day of month
financial year
```

Canonical analytical key:

```text
monthKey = YYYY-MM
```

Example:

```text
2026-08
```

Display-only value:

```text
Aug-26
```

This prevents textual sorting errors.

---

# 11. Financial Year Resolution

For Indian financial-year reporting:

```text
April → March
```

Example:

```text
2026-04-01 through 2027-03-31
→ FY2026-27
```

Therefore:

```text
24-Aug-2026
→ FY2026-27
```

and:

```text
15-Feb-2027
→ FY2026-27
```

Financial Year should be derived internally from the canonical policy-issued date.

---

# 12. Legacy Month Validation

If the v8.1-compatible upload still contains:

```text
Month = Aug-26
```

the pipeline should compare:

```text
uploaded Month
vs
derived monthLabel
```

Possible result:

```text
MATCH
MISMATCH
NOT_SUPPLIED
```

A mismatch should create a Data Quality finding.

It should **not** override the internally derived month.

---

# 13. Legacy Day Validation

Likewise:

```text
uploaded Day
vs
derived day
```

Example:

```text
POLICY ISSUED DATE = 24-Aug-2026
Uploaded Day       = 23
Derived Day        = 24
```

Canonical result:

```text
day = 24
```

Data Quality:

```text
LEGACY_DAY_MISMATCH
```

---

# 14. Bank Resolution

Bank should resolve before Branch because durable Branch identity depends on:

```text
Bank + Branch Code
```

Recommended bank resolution priority:

```text
1. Exact Bank ID / configured bank code
2. Normalized configured bank name
3. Known alias
4. UNCONFIGURED
```

Possible status:

```text
MATCHED_ID
MATCHED_NAME
MATCHED_ALIAS
UNCONFIGURED
AMBIGUOUS
```

---

# 15. Unconfigured Bank

When a transaction bank cannot be resolved:

```text
bankId = UNCONFIGURED
```

The transaction must remain analytically visible.

This preserves the v8.1 behavior that unknown banks should not disappear from the `ALL` view.

Do not:

```text
discard record
```

or:

```text
assign to nearest-looking bank
```

---

# 16. Branch Resolution

Preferred branch-resolution input:

```text
resolved bankId
+
BRANCH CODE
```

Canonical key:

```text
bankId:branchCode
```

Example:

```text
IB:00123
```

Resolution priority:

```text
1. Bank + Branch Code exact
2. explicitly approved migration fallback
3. UNMAPPED
```

---

# 17. Branch Name Fallback

During migration from v8.1 data, some source rows may lack a reliable Branch Code.

A carefully controlled fallback may use:

```text
Bank + normalized Branch Name
```

but must be classified differently.

Possible status:

```text
MATCHED_EXACT
MATCHED_FALLBACK
UNMAPPED
AMBIGUOUS
```

Fallback matches should generate a Data Quality warning or provenance marker.

They must not be indistinguishable from exact durable-ID matches.

---

# 18. Ambiguous Branch Resolution

Example:

```text
Uploaded branch name:
MAIN BRANCH

Two Branch Master candidates:
IB:00123
IB:00456
```

Resolution:

```text
branchId = UNMAPPED
status   = AMBIGUOUS
```

Do not choose one arbitrarily.

This embodies the rule:

> Unknown is better than wrong.

---

# 19. Branch Master as Geography Authority

Once a branch resolves, the Branch Master becomes an important source of geography.

Example:

```text
Branch IB:00123
    ↓
stateId = IN-AS
```

This can be compared against the uploaded transaction State.

If:

```text
Uploaded State = Assam
Branch State    = Assam
```

everything agrees.

If:

```text
Uploaded State = Meghalaya
Branch State    = Assam
```

the discrepancy becomes a Data Quality conflict.

---

# 20. Geography Resolution Priority

Recommended geography logic:

```text
If Branch resolves:
    use BranchMaster.stateId
    ↓
    resolve Zone from GeographyMaster

Else:
    attempt State resolution from uploaded STATE
    ↓
    resolve Zone from GeographyMaster
```

This gives us two pathways:

```text
Branch → State → Zone
```

preferred, and:

```text
Uploaded State → State Master → Zone
```

fallback.

---

# 21. State Resolution

Possible State status:

```text
MATCHED_BRANCH
MATCHED_STATE_ID
MATCHED_STATE_NAME
MATCHED_ALIAS
UNMAPPED
AMBIGUOUS
```

The resolver should preserve provenance.

Example:

```javascript
stateResolution: {
  value: "IN-AS",
  status: "MATCHED_BRANCH",
  source: "BRANCH_MASTER"
}
```

---

# 22. Zone Resolution

Zone should be derived from resolved State via Geography Master.

Canonical logic:

```text
resolved stateId
      ↓
Geography Master
      ↓
zoneId
```

Do not derive Zone directly from the uploaded Zone field.

The uploaded Zone becomes a validation/reference field only.

---

# 23. Legacy Zone Validation

Example:

```text
Uploaded State: Assam
Uploaded Zone:  North

Geography Master:
Assam → East
```

Canonical:

```text
zoneId = EAST
```

Data Quality:

```text
LEGACY_ZONE_MISMATCH
```

This is one of the central changes from v8.1 to v8.2.

---

# 24. Geography Master Missing

If no Geography Master exists:

```text
zone resolution status:
MASTER_ABSENT
```

This is different from:

```text
UNMAPPED
```

where a Geography Master exists but the State cannot be resolved.

This semantic distinction must remain visible to Data Quality.

---

# 25. RM Resolution

Preferred RM ownership for Branch analytics should come from:

```text
Branch Assignment Master
```

rather than blindly trusting the RM field in each transaction.

Resolution:

```text
resolved branchId
      ↓
Branch Assignment
      ↓
rmId
```

If effective dating is enabled:

```text
branchId + policyIssuedDate
      ↓
valid assignment
```

---

# 26. Uploaded RM vs Assigned RM

The uploaded PR row may contain:

```text
RM CODE
RM NAME
```

These should be compared with the resolved Branch Assignment.

Example:

```text
Uploaded RM = RM002
Branch Assignment = RM004
```

Canonical branch-owner RM:

```text
RM004
```

Potential Data Quality:

```text
TRANSACTION_RM_ASSIGNMENT_CONFLICT
```

However, this policy should be applied carefully because transaction ownership and branch mapping may have legitimate operational exceptions.

Therefore the system should preserve both concepts:

```text
sourceRmId
assignedRmId
```

where needed.

---

# 27. Important RM Semantic Decision

We should distinguish:

### Source RM

The RM identity recorded on the transaction.

### Assigned RM

The RM currently/historically responsible for the branch according to master data.

They are not automatically the same business concept.

Therefore v8.2 should not erase the source RM.

This becomes particularly important when:

- branch reassignment occurs;
- a relieving RM books business;
- temporary support exists;
- source mapping is stale;
- historical assignment differs.

---

# 28. Canonical RM for Analytics

The exact analytical choice may vary by metric.

For example:

### Sales-origin productivity

May prefer:

```text
sourceRmId
```

### Branch ownership / portfolio management

May prefer:

```text
assignedRmId
```

This is a major semantic issue and should not be hard-coded invisibly.

For the initial v8.2 architecture:

```text
preserve both
```

and allow analytics to explicitly choose.

---

# 29. Hierarchy Resolution

Once the relevant RM is identified:

```text
RM
 ↓
CSM
 ↓
ASM
 ↓
ZSM
 ↓
National Head
```

The resolver traverses:

```text
employeeId → managerId
```

using the hierarchy relationship master.

Conceptually:

```javascript
resolveHierarchy(rmId, transactionDate);
```

returns:

```javascript
{
  rmId: "RM00482",
  csmId: "CSM0021",
  asmId: "ASM0007",
  zsmId: "ZSM0003",
  nationalHeadId: "NH0001"
}
```

---

# 30. Effective-Date Hierarchy

If hierarchy relationships contain:

```text
validFrom
validTo
```

then the resolver should eventually use:

```text
POLICY ISSUED DATE
```

to identify the historically valid management chain.

Example:

```text
RM00482
reported to ASM01 until 30-Sep
reported to ASM02 from 01-Oct
```

September business should remain under ASM01 when historical resolution is enabled.

The architecture must support this even if the first implementation initially operates on current mappings.

---

# 31. Hierarchy Failure States

Possible statuses:

```text
RESOLVED
PARTIAL
EMPLOYEE_UNMAPPED
MANAGER_MISSING
ROLE_MISMATCH
CYCLE_DETECTED
MASTER_ABSENT
```

Example:

```text
RM → CSM → ASM
```

but no ZSM relationship:

```text
hierarchyStatus = PARTIAL
```

Do not discard the valid portion.

---

# 32. Product Resolution

Preferred product identity:

```text
PRODUCT CODE
```

through Product Master when available.

Resolution:

```text
Product Code
     ↓
Product Master
     ↓
Product ID
Product Name
LOB
```

Fallback during migration:

```text
normalized Product Name
```

Possible status:

```text
MATCHED_CODE
MATCHED_NAME
UNMAPPED
AMBIGUOUS
MASTER_ABSENT
```

---

# 33. Product Code ↔ Name Conflict

If:

```text
PRODUCT CODE = H001
Uploaded Product Name = Product A
Product Master H001   = Product B
```

Canonical value should use the configured Product Master when that master is authoritative.

Data Quality:

```text
PRODUCT_NAME_CONFLICT
```

Again, the source value should remain inspectable.

---

# 34. LOB Resolution

Where Product Master is configured:

```text
Product
   ↓
LOB
```

should be the preferred source.

If Product Master is absent, existing v8.1 uploaded LOB may remain the fallback.

Possible provenance:

```text
PRODUCT_MASTER
SOURCE_PR
UNMAPPED
```

---

# 35. Premium Handling

Premium must be normalized numerically but otherwise preserved.

Examples:

```text
12500   → 12500
0       → 0
-2500   → -2500
```

Do not automatically:

```text
abs(premium)
```

or:

```text
remove negative values
```

The v8.1 semantic distinction between positive, zero and negative premium must remain intact.

# 38. Resolution Confidence

Some resolution methods are stronger than others.

Potential confidence levels:

```text
EXACT
DERIVED
FALLBACK
AMBIGUOUS
UNRESOLVED
```

Example:

```text
Bank + Branch Code
→ EXACT
```

```text

→ FALLBACK
```

```text
State derived from exact Branch Master
→ DERIVED
```

This does not necessarily need to appear in the UI initially, but the architecture should support it.

# 42. Row-Level Resolution State

Each processed row should conceptually finish with:

```text
READY
READY_WITH_WARNINGS
INVALID
```

### READY

Suitable for canonical analytics with no material resolution concern.

### READY_WITH_WARNINGS

Suitable for analytics, but with noteworthy Data Quality findings.

### INVALID

Cannot safely enter ordinary analytical calculations.

The exact treatment of invalid rows should be centrally defined rather than dashboard-specific.

# 44. Master-Absence Behavior

v8.2 must remain usable during migration even if not all masters are configured.

For example:

```text
Branch Master absent
```

should not necessarily make PR upload impossible.

Instead:

```text
branchResolution = MASTER_ABSENT
```

and existing source-based analytics may temporarily continue where safe.

This is central to introducing v8.2 incrementally without destabilizing v8.1 functionality.

# 48. Enrichment Pipeline API

Conceptually:

```javascript
enrichTransaction(rawRow, context);
```

where context contains:

```javascript
{
  (activeMasters, lookupMaps, configuration);
}
```

returns:

```javascript
{
  (status, canonicalRecord, findings);

```

---

# 49. Pure-Function Preference

Where possible, enrichment/resolution functions should be pure.

Meaning:

```text
same input + same masters
→ same output
```

Resolvers should not:

- alter global state;
- manipulate DOM;
- save to IndexedDB;
- change filters;
- generate random identifiers unnecessarily.

This will make testing much easier.

---

# 50. Deterministic Resolution

A row processed today and tomorrow against the same active masters should resolve identically.

The only accepted reasons for changed output should be:

- source row changed;
- active master changed;
- resolver rules changed deliberately.

This is vital for reproducibility.

---

# 51. Analytics Boundary

After enrichment, analytics should consume canonical dimensions.

For example, instead of:

```text
raw row.STATE
```

future analytics should use:

```text
canonical.stateId
```

Instead of:

```text
raw row.Month
```

use:

```text
canonical.monthKey
```

Instead of:

```text
raw row.Zone
```

use:

```text
canonical.zoneId
```

This is how v8.2 removes Excel-derived dependency safely.

---

# 52. Compatibility Boundary

During the migration period:

```text
v8.1 analytics
```

may continue consuming legacy normalized records while:

```text
v8.2 enrichment pipeline
```

is independently tested.

Only after output reconciliation should modules be switched one by one.

This gives us:

```text
Old path
and
New path
```

temporarily in parallel.

---

# 53. Reconciliation Testing

Before replacing an existing v8.1 analytical path, compare:

```text
v8.1 result
vs
v8.2 canonical result
```

for metrics expected to remain semantically unchanged.

Examples:

```text
total premium
bank contribution
current-period premium
positive / zero / negative counts
known bank totals
```

Differences must be explained before migration.

# 54. Expected Intentional Differences

Some differences are expected and desirable.

Example:

```text

```

v8.1 may classify according to uploaded Month.

v8.2 should classify:

```text
Aug-26
```

This is an intentional data-source correction and should be documented.

# 60. Step 1D Architecture Decisions

The following decisions should now be considered locked:

1. `POLICY ISSUED DATE` is authoritative for Month, Day and Financial Year.
2. Uploaded Month and Day become legacy validation fields.
3. Zone is internally derived from resolved State / Geography Master.
4. Uploaded Zone becomes non-authoritative validation data.
5. Bank resolves before Branch.
6. Branch identity prefers Bank + Branch Code.
7. Name-based branch matching is migration fallback only.
8. Ambiguous mapping must not be guessed.
9. Branch Master is preferred for branch geography.
10. Geography Master is authoritative for State→Zone.
11. Missing master and unmapped value are distinct.
12. Source RM and Assigned RM are separate concepts.
13. Hierarchy traversal is relationship-based.
14. Effective dates are supported architecturally.
15. Product Master becomes authoritative when configured.
16. Premium sign is preserved.
17. Canonical records carry resolution provenance.
18. Data Quality findings are structured.
19. Enrichment functions should be deterministic and independently testable.
20. Existing v8.1 analytics are migrated only after reconciliation.
21. Canonical dimensions become the future analytical source of truth.
